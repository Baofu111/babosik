# Бабосік — Product Brief

## Що це

Веб-застосунок для особистого фінансового менеджменту. Автоматичний імпорт транзакцій з Monobank, ручне введення, категоризація, аналітика та рекомендації.

Тон: дружній, без зайвого фінтех-пафосу.

---

## Аудиторія

Вік 25–45. Люди, які хочуть навести лад у витратах, але яким недостатньо виписки з банку. Потрібна гнучкість: власні категорії, фільтри, візуалізація.

---

## Контекст

Є робочий Telegram-бот (Python) який:
- Тягне транзакції через Monobank API
- Категоризує через AI
- Дозволяє змінювати категорію / підкатегорію / теги
- Зберігає дані в Google Sheets
- Автодеплой через GitHub

Бабосік — окремий продукт з власною БД. Бот залишається, але дані мігруємо в Supabase.

---

## MVP — Must Have

- [ ] Авторизація (Google OAuth або email через Supabase Auth)
- [ ] Підключення Monobank API — автоімпорт транзакцій
- [ ] Ручне додавання транзакцій
- [ ] Редагування та видалення транзакцій
- [ ] Управління категоріями та підкатегоріями (CRUD)
- [ ] Теги на транзакціях
- [ ] Аналітика: витрати по категоріях за місяць
- [ ] Порівняння місяць-до-місяця
- [ ] Топ витрат

> **Рішення 2026-07-17:** «Ручне додавання транзакцій» лишається у MVP (раніше `jtbd.md` і
> `sitemap.md` тримали його в backlog як кандидата на виліт). Причина — готівка ~34,6% суми
> операцій (`research/research.md → Доресерч п.2`): без неї «повна картина» неповна. Обсяг —
> **мінімальний**: сума + категорія, контекстний вхід зі Списку транзакцій. Формулювання цінності
> більше не обіцяє «нуль ручного введення» — акцент «без рутини» (`voices/docs/voice.md`).

## Висновки дослідження

→ Повний research: [`research/research.md`](research/research.md) · [`research/research.html`](research/research.html)

### Що хочуть користувачі

- **Автоматизація + контроль**: не вводити вручну, але мати змогу виправити і перекатегоризувати
- **Свої категорії**: стандартні не підходять — це must have, не nice-to-have
- **Аналітика з першого погляду**: без фінансової освіти, без зусиль
- **Дружній тон**: не банківська суворість

### UX-патерн — Snapshot / Summary-first (дашборд)

Вибір обґрунтований трьома причинами:
1. MVP-вимоги (аналітика по категоріях, порівняння місяць-до-місяця, топ витрат) — це і є дашборд
2. Швидкість без спінерів — агрегати кешуються
3. Десктоп як основний екран — дашборд масштабується природно

**Якщо категорій 10+** — додати treemap як альтернативний вигляд (перемикач List / Map).
**Бюджети та цілі (Goal/Budget Contrast)** — не реалізовувати в MVP, система виглядає зламаною без даних.

## Інформаційна архітектура

→ Повна ІА: [`concept/sitemap.md`](concept/sitemap.md) · [`concept/flows.md`](concept/flows.md) · [`research/ia.html`](research/ia.html)

Виведена з jobs (`research/jtbd.md`), а не зі структури конкурентів.

### Sitemap верхнього рівня

```
Бабосік
├─ Вхід / Реєстрація              [onboarding-крок, не призначення]
├─ ① Огляд за місяць              MJ + RJ-3   ← домашній екран
│    └ Порівняння місяців         RJ-4
├─ ② Транзакції → Правка          RJ-2
├─ ③ Категорії та підкатегорії    RJ-2  (диференціатор, ядро MVP №1)
└─ ④ Підключення банків           RJ-1  (+ RJ-5 перший раз)
Backlog: ручне додавання, експорт даних
```

### Глобальна навігація (4 входи)

| Пункт | Job-кластер |
|-------|-------------|
| **Огляд** *(home)* | `MJ` + `RJ-3` + `RJ-4` — розуміти картину |
| **Транзакції** | `RJ-2` — виправити подію |
| **Категорії** | `RJ-2` — своя класифікація |
| **Акаунт** *(утиліта)* | `RJ-1` банки (глибоко) + вхід |

### Глибина до main job

- **Main job (`MJ`) = Огляд = домашній екран → 0 тапів.**
- `RJ-3`: 0 (в Огляді) · `RJ-4`: 1 (перемикач) · `RJ-2`: 2 контекстно / 3 навігацією · `RJ-1`: 3 (рідкісне).

### Main flow (`RJ-1` + onboarding)

Реєстрація → Підключити банк → *(loading)* → **Огляд за місяць** (одразу реальні дані, без «налаштуй спочатку»).
Порожній Огляд **ніколи не голий**: пропонує дію (оновити / підключити ще банк) — захист від `RJ-5` blank-state.

### Принципи, що випливають з ІА

- **Огляд несе 6 jobs** — найгустіший вузол, стежити за перевантаженням на вайрфреймах.
- Кожен екран має стани empty / error / loading; тупиків без виходу немає (див. `flows.md`).
- **EJ-1 «контроль, не провина»** — наскрізна якість тону, не екран.

## Вайрфрейми

→ Усі екрани: [`wireframes/`](wireframes/) · правила: [`wireframes/_conventions.md`](wireframes/_conventions.md) · замовлення: [`wireframes/_screens.md`](wireframes/_screens.md) · критика: [`wireframes/_critique.md`](wireframes/_critique.md)

Клікабельний **grey-box** прототип усіх флоу продукту: лише структура / ієрархія / зони — без кольору, шрифтів, іконок, тіней (це кроки tokens / design-system).

- **Покриття:** усі екрани зі sitemap — Вхід/Реєстрація, Підключення банків, Огляд за місяць, Список транзакцій, Транзакція: правка, Категорії та підкатегорії, Порівняння місяців (+ backlog-заглушки: додати вручну, експорт). 28 сторінок.
- **Стани:** кожен екран — базова сторінка (успіх) + окремі `-empty` / `-error` / `-loading` за реальними станами з `flows.md`. Кожен стан має вихід — жодних глухих кутів (`error → спробувати ще`, `empty → дія`, `loading → успіх + збій`).
- **Навігація:** ліва панель-дерево ([`wireframes/wf-nav.js`](wireframes/wf-nav.js)) — усі екрани й стани, спільна на кожній сторінці; угорі кожної — перемикач станів екрана.
- **Зв'язки:** головна дія кожного екрана — справжній `<a href>` на наступний крок за маршрутами `flows.md`; розвилки ведуть в обидва боки.
- **Іменування:** `wireframes/<slug>.html` (успіх) + `<slug>-<стан>.html`.

Наступні кроки: design tokens (колір / типографіка) → design system → handoff → dev.

## Голос (текст продукту)

→ Правила: [`voices/docs/voice.md`](voices/docs/voice.md) · увесь текст (джерело правди): [`voices/docs/microcopy.md`](voices/docs/microcopy.md)

Як продукт говорить. Виведено з персон і мови конкурентів (`research/research.md → Мова конкурентів`).

**4 принципи:**
1. **Описуємо, не судимо** — факти про гроші, без оцінки людини (EJ-1).
2. **Роботу робить продукт, а не наказ користувачу** — не «візьми контроль» (кластер конкурентів), а «ось твоя картина» (RJ-5).
3. **Довіра важливіша за дотепність** — гроші + майбутній спільний доступ; просто і спокійно.
4. **У помилці — що сталось і що вціліло** — факт + «Дані не втрачено» + один вихід (EJ-2).

**Словник (одне поняття — одне слово):** звертання **«ти»** скрізь (без родозалежного минулого часу); банки повними назвами (**Monobank**, **ПриватБанк**); дії — одне ім'я («Спробувати ще», «До огляду», «Підключити банк», «Додати категорію», «Зберегти»); завантаження — активне «ми-» дієслово; місяці з малої, дата «30 червня 2026».

**Заборонене:** AI-кліше («Ой, щось пішло не так»), вітання («Вітаємо!»), мотиваційний тон («візьми контроль»), оклики, емодзі в системних повідомленнях, слово «успішно», job-коди й жаргон у видимому тексті.

Застосовано до всіх 28 сторінок `wireframes/`; текст звірено наскрізь (одна дія = одне ім'я).

## Збірка UI

→ Дизайн-система в коді: [`ui/`](ui/) · вітрина: [`ui/kit.html`](ui/kit.html) · оболонка: [`ui/shell.html`](ui/shell.html) · реєстр: [`ui/inventory.md`](ui/inventory.md) · вдягнені екрани: [`concept/neo-mirai/`](concept/neo-mirai/)

Візуальний напрям — **NEO MIRAI** (тепла естетика: корал=сонце, золото=амбер, петроль=глибина), накладений шаром поверх мови «Ясність» (`concept.md`). Закон «колір не судить суму» збережено.

- **`ui/kit.css`** — ЄДИНЕ ПЛАСКЕ джерело стилів (урок 7): `@import` `tokens/tokens.css` + шрифти, `:root` NM-шар (`--nm-*`, `--panel`, `--ease-out`) і класи компонентів. Без розколу на три рівні токенів (урок 8). Підключаєш один файл — і все.
- **`ui/shell.html`** — оболонка як РОЗМІТКА: таб-бар (`.side`, ≤900px → горизонталь) + двошарова шапка (`.page-head` → `.ph-context` + `.ph-bar`) + слот `.work`. Кожен екран бере каркас звідси.
- **`ui/kit.html`** — вітрина всіх компонентів у станах; **джерело правди розмітки** компонента.
- **`ui/inventory.md`** — реєстр класів. Бракує компонента → спершу сюди + `kit.css`, тоді на екран.
- **`concept/neo-mirai/`** — 30 екранів, вдягнених у кіт (7 success + 21 стан empty/error/loading + 2 backlog). Структуру й текст беруть із `wireframes/` (grey-box лишається референсом, його не чіпаємо), вигляд — лише з класів кіта. Кожен лінкує `../../ui/kit.css`.

Значення (колір/відступ/розмір) живуть у `:root` `ui/kit.css` (та примітиви — в `tokens/tokens.css`); правка там розноситься на всі екрани сама. Пласку структуру, painted=еталон і зведення дрейфу назв (`.flag→.tag-*`, `.cards→.breakdown/.top/.tx-list`) описано в шапці `kit.css`.

## Робоче правило: «залишаємо» (візуальні правки)

Коли користувач каже **«залишаємо»** щодо візуальної правки:

1. Правку роблю в **кіті**, не на екрані: `ui/kit.css` (усі значення — через змінні `:root`) + вітрина `ui/kit.html` (еталонна розмітка компонента).
2. Причину підписую в `tokens/DESIGN.md`.
3. **Зміна значення** в `ui/kit.css` розноситься на всі екрани сама — екрани його споживають, більше нічого робити не треба.
4. **Зміна розмітки** компонента — переношу вручну на **кожен екран у `concept/neo-mirai/`**, де цей компонент стоїть; джерело правди розмітки — `ui/kit.html`. Правка розмітки на одному екрані розсинхронізує набір — так не робимо.
5. Бракує компонента — спершу додаю в `ui/kit.css` + `ui/inventory.md`, тоді на екран.
