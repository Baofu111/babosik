# Бабосік — Product Brief

## Що це

Веб-застосунок для особистого фінансового менеджменту. Автоматичний імпорт транзакцій з Monobank, ручне введення, категоризація, аналітика та рекомендації.

Тон: дружній, без зайвого фінтех-пафосу.

---

## Аудиторія

Вік 25–45. Люди, які хочуть навести лад у витратах, але яким недостатньо виписки з банку. Потрібна гнучкість: власні категорії, фільтри, візуалізація.

---

## Контекст

Є робочий Telegram-бот (Python) який:
- Тягне транзакції через Monobank API
- Категоризує через AI
- Дозволяє змінювати категорію / підкатегорію / теги
- Зберігає дані в Google Sheets
- Автодеплой через GitHub

Бабосік — окремий продукт з власною БД. Бот залишається, але дані мігруємо в Supabase.

---

## MVP — Must Have

- [ ] Авторизація (Google OAuth або email через Supabase Auth)
- [ ] Підключення Monobank API — автоімпорт транзакцій
- [ ] Ручне додавання транзакцій
- [ ] Редагування та видалення транзакцій
- [ ] Управління категоріями та підкатегоріями (CRUD)
- [ ] Теги на транзакціях
- [ ] Аналітика: витрати по категоріях за місяць
- [ ] Порівняння місяць-до-місяця
- [ ] Топ витрат

## Наступні ітерації

- Мультикористувачі / спільний доступ (архітектурно закладено)
- Інші банки (ПриватБанк, інші)
- AI-рекомендації
- Бюджети та цілі
- Мобільний застосунок

## Технічний стек

| Шар | Технологія | Причина |
|-----|-----------|---------|
| Frontend + API | Next.js 14 (App Router) | Один репо, SSR, найбільша екосистема |

## Архітектура БД (базова)

```
users
  id, email, created_at

bank_connections
  id, user_id, bank (mono/privat), token_encrypted, created_at

transactions
  id, user_id, external_id, amount, currency, description,
  date, category_id, subcategory_id, source (auto/manual), created_at

categories
  id, user_id, name, color, icon, is_default

subcategories
  id, category_id, name

tags
  id, user_id, name

transaction_tags
  transaction_id, tag_id
```

user_id скрізь — архітектурна готовність до мультиюзерності.

---

## Деплой та CI/CD

```
push to main
  → GitHub Actions: lint + typecheck + unit tests
  → якщо OK: Vercel auto-deploy
  → якщо fail: деплой блокується, нотифікація
```

## Дизайн-принципи

- Mobile-first, але десктоп — основний
- Дружній тон, без банківської суворості
- Темна / світла тема
- Швидкість: дані мають завантажуватись без спінерів де можливо

---

## Що НЕ робимо в MVP

- Мобільний app (тільки адаптив)
- Сімейний/спільний доступ (закладено архітектурно, не реалізовано)
- Складні AI-фічі
- Мультивалютна аналітика (показуємо в UAH)

## Висновки дослідження

→ Повний research: [`research/research.md`](research/research.md) · [`research/research.html`](research/research.html)

### Що хочуть користувачі

- **Автоматизація + контроль**: не вводити вручну, але мати змогу виправити і перекатегоризувати
- **Свої категорії**: стандартні не підходять — це must have, не nice-to-have
- **Аналітика з першого погляду**: без фінансової освіти, без зусиль
- **Дружній тон**: не банківська суворість

### UX-патерн — Snapshot / Summary-first (дашборд)

Вибір обґрунтований трьома причинами:
1. MVP-вимоги (аналітика по категоріях, порівняння місяць-до-місяця, топ витрат) — це і є дашборд
2. Швидкість без спінерів — агрегати кешуються
3. Десктоп як основний екран — дашборд масштабується природно

**Якщо категорій 10+** — додати treemap як альтернативний вигляд (перемикач List / Map).
**Бюджети та цілі (Goal/Budget Contrast)** — не реалізовувати в MVP, система виглядає зламаною без даних.

## Інформаційна архітектура

→ Повна ІА: [`concept/sitemap.md`](concept/sitemap.md) · [`concept/flows.md`](concept/flows.md) · [`research/ia.html`](research/ia.html)

Виведена з jobs (`research/jtbd.md`), а не зі структури конкурентів.

### Sitemap верхнього рівня

```
Бабосік
├─ Вхід / Реєстрація              [onboarding-крок, не призначення]
├─ ① Огляд за місяць              MJ + RJ-3   ← домашній екран
│    └ Порівняння місяців         RJ-4
├─ ② Транзакції → Правка          RJ-2
├─ ③ Категорії та підкатегорії    RJ-2  (диференціатор, ядро MVP №1)
└─ ④ Підключення банків           RJ-1  (+ RJ-5 перший раз)
Backlog: ручне додавання, експорт даних
```

### Глобальна навігація (4 входи)

| Пункт | Job-кластер |
|-------|-------------|
| **Огляд** *(home)* | `MJ` + `RJ-3` + `RJ-4` — розуміти картину |
| **Транзакції** | `RJ-2` — виправити подію |
| **Категорії** | `RJ-2` — своя класифікація |
| **Акаунт** *(утиліта)* | `RJ-1` банки (глибоко) + вхід |

### Глибина до main job

- **Main job (`MJ`) = Огляд = домашній екран → 0 тапів.**
- `RJ-3`: 0 (в Огляді) · `RJ-4`: 1 (перемикач) · `RJ-2`: 2 контекстно / 3 навігацією · `RJ-1`: 3 (рідкісне).

### Main flow (`RJ-1` + onboarding)

Реєстрація → Підключити банк → *(loading)* → **Огляд за місяць** (одразу реальні дані, без «налаштуй спочатку»).
Порожній Огляд **ніколи не голий**: пропонує дію (оновити / підключити ще банк) — захист від `RJ-5` blank-state.

### Принципи, що випливають з ІА

- **Огляд несе 6 jobs** — найгустіший вузол, стежити за перевантаженням на вайрфреймах.
- Кожен екран має стани empty / error / loading; тупиків без виходу немає (див. `flows.md`).
- **EJ-1 «контроль, не провина»** — наскрізна якість тону, не екран.
